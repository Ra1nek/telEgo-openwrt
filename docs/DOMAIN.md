<p align="center"><a href="DOMAIN.md"><strong>Русский</strong></a> · <a href="DOMAIN_EN.md">English</a></p>

Это руководство описывает полный путь от выбора домена до рабочей DNS-схемы для `telEgo-openwrt` на роутере OpenWrt. Оно не привязано к конкретному регистратору или DNS-провайдеру и подходит как для международных доменных зон, так и для национальных TLD.

В проекте домен используется прежде всего для двух задач: постоянного HTTPS-имени Telegram WEB Proxy и стабильного имени для direct MTProto/MTProxy при динамическом публичном WAN IP. Если WEB Proxy публикуется через Tunnel, внешний HTTPS-порт `443` завершается на стороне Tunnel-провайдера и не требует занимать WAN TCP/443 самого OpenWrt. Для direct MTProto/MTProxy доменное имя может автоматически следовать за меняющимся публичным IP через DDNS.

> [!NOTE]
> Информация проверена на **11 сентября 2026 года**. Стоимость доменов, способы оплаты, поддерживаемые TLD и требования registry/registrar со временем меняются. Перед регистрацией всегда проверяйте актуальные условия у выбранного провайдера.

## Назначение домена в `telEgo-openwrt`

| Сценарий | Что даёт домен | Типичный DNS-механизм | Важное ограничение |
|---|---|---|---|
| **WEB Proxy** | Постоянный HTTPS hostname | Tunnel или обычная DNS-запись | При Tunnel-схеме WAN TCP/443 OpenWrt не требуется |
| **Direct MTProto/MTProxy** | Стабильное имя при меняющемся WAN IP | `A` / `AAAA` + DDNS | Для прямого входящего соединения нужен маршрутизируемый публичный IP |
| **Администрирование DNS** | Единая точка управления именами сервисов | Authoritative DNS provider | Регистратор и DNS-провайдер могут быть разными компаниями |

Типовая схема имён:

```text
web.example.com  -> WEB Proxy
mt.example.com   -> direct MTProto/MTProxy
```

### WEB Proxy через Tunnel

```text
Telegram client
      |
      | HTTPS :443
      v
Tunnel provider edge
      |
      | encrypted tunnel
      v
connector on OpenWrt
      |
      v
local WEB Proxy
```

В такой схеме пользователь подключается к стандартному HTTPS-порту `443`, но этот порт не требуется открывать или занимать на WAN-интерфейсе OpenWrt. Поэтому публичный `443` не конфликтует с HTTPS-интерфейсом роутера или другим локальным сервисом.

### Direct MTProto/MTProxy

```text
Telegram client
      |
      v
mt.example.com
      |
      | A / AAAA
      v
public WAN IP of OpenWrt
      |
      v
direct MTProto/MTProxy
```

Если публичный WAN IP динамический, DDNS-клиент обновляет соответствующую `A` или `AAAA` запись после смены адреса.

> [!IMPORTANT]
> DDNS решает только проблему **меняющегося публичного IP**. Он не устраняет конфликт портов и не делает CGNAT публичным. Для direct MTProto/MTProxy провайдер должен выдавать маршрутизируемый публичный адрес либо должна использоваться другая технология входящей доступности. Если WAN TCP/443 уже занят, direct proxy необходимо назначить другой свободный порт.

## Маршрут настройки

| Этап | Результат |
|---|---|
| **1. Выбрать TLD** | Определена подходящая доменная зона |
| **2. Выбрать регистратора** | Понятны цена, продление, оплата и требования к владельцу |
| **3. Зарегистрировать домен** | Домен появляется в панели registrar |

| **8. Включить DNSSEC** | DNS-ответы получают криптографическую проверку |

## 1. Что понадобится

Для регистрации достаточно домена и доступа к его панели управления. Для direct MTProto/MTProxy дополнительно понадобится публичный WAN IP или другой способ обеспечить входящую доступность.

Примеры:

```text
example.com
example.net
example.org
<имя>.ru
```

Покупать web hosting, арендовать VPS или приобретать отдельный TLS-сертификат только ради регистрации домена не требуется.

После регистрации можно создавать отдельные поддомены для сервисов:

```text
web.example.com
mt.example.com
status.example.com
```

Конкретные имена выбираются пользователем самостоятельно.

## 2. Выбор доменной зоны

Часть доменного имени после последней точки называется **TLD — Top-Level Domain**.

```text
example.com  -> .com
example.org  -> .org
<имя>.ru     -> .ru
```

Универсально лучшей доменной зоны нет. При выборе учитывайте:

- доступность нужного имени;
- стоимость регистрации;
- стоимость обычного продления;
- правила конкретного TLD;
- возможность регистрации из вашей страны;
- доступные способы оплаты;
- удобство управления доменом;
- требования к владельцу или администратору домена.

Для технических сервисов часто подходят `.com`, `.net`, `.org` и другие generic TLD. Национальный ccTLD также может быть хорошим выбором, если его правила подходят владельцу домена.

> [!TIP]
> Не выбирайте домен только по рекламной цене первого года. Для постоянно работающего сервиса условия продления, восстановление доступа и контроль над доменом важнее разовой скидки.

---

## 3. Выбор регистратора

**Регистратор** — компания, через которую домен регистрируется, продлевается и переносится. DNS необязательно должен обслуживаться той же компанией.

Перед оплатой проверьте:

- поддерживается ли нужный TLD;
- можно ли зарегистрировать его из вашей страны;
- доступен ли подходящий способ оплаты;
- сколько стоит первый период и обычное продление;
- можно ли менять authoritative nameservers (`NS`);
- поддерживается ли DNSSEC;
- доступна ли MFA/2FA;
- понятна ли процедура transfer-out;
- какие документы или подтверждение личности требуются владельцу.

### Международные регистраторы

Для международных TLD можно рассмотреть, например:

- Cloudflare Registrar;
- Namecheap;
- Porkbun;
- другого ICANN-accredited registrar.

Это примеры, а не обязательный список для `telEgo-openwrt`. Выбор зависит от страны пользователя, нужного TLD, цены продления, способов оплаты и требований аккаунта.

Cloudflare Registrar, например, поддерживает более 400 TLD, но не все существующие доменные зоны. Если нужная зона отсутствует в поиске регистрации, приобрести её через Cloudflare Registrar нельзя.

### Национальные доменные зоны

У ccTLD могут быть собственные требования registry, включая:

- гражданство или место проживания;
- local presence или адрес;
- регистрацию юридического лица;
- идентификацию владельца;
- специальные transfer rules;
- дополнительные правила DNSSEC или контактных данных.

Перед покупкой национального домена изучите правила соответствующего registry.

## 4. Особенности для пользователей из России

Для пользователей из России особенно важно отдельно проверить **доступность TLD** и **возможность оплаты**.

Международный registrar не обязан:

- поддерживать `.ru`, `.рф` или `.su`;
- предоставлять все продукты аккаунтам из России;
- принимать карты российских банков;
- поддерживать конкретный способ оплаты, доступный пользователю.

Поэтому для российских национальных доменов часто проще использовать российского регистратора, а DNS при необходимости передать отдельному DNS-провайдеру.

Для `.ru`, `.рф` и `.su` можно рассмотреть, например:

- Timeweb;
- Рег.ру;
- RU-CENTER;
- другого регистратора, аккредитованного для нужной зоны.

### Идентификация `.RU`, `.РФ` и `.SU`

С **1 сентября 2026 года** для управления доменами `.RU`, `.РФ` и `.SU` требуется идентификация администратора через ЕСИА («Госуслуги»).

Она требуется для значимых операций, включая:

- регистрацию;
- продление;
- смену регистратора;
- смену администратора;
- изменение данных администратора;
- делегирование домена и смену NS-серверов.

Для физического лица обычно требуется подтверждённая учётная запись Госуслуг.

> [!IMPORTANT]
> Если планируется использовать `.ru`, `.рф` или `.su`, пройдите необходимую идентификацию **до изменения DNS/NS**. Без неё регистратор может заблокировать операцию управления доменом.

Если требования конкретного национального TLD выполнить невозможно, практичнее выбрать другую доступную доменную зону.

## 5. Общий порядок регистрации домена

Интерфейс у разных registrars отличается, но последовательность действий обычно одинакова.

1. Откройте сайт выбранного регистратора.
2. Создайте учётную запись.
3. Включите MFA/2FA, если она доступна.
4. Откройте поиск или регистрацию домена.
5. Введите желаемое имя и проверьте его доступность.
6. Выберите TLD.
7. Укажите данные владельца или администратора домена.
8. Пройдите идентификацию, если её требует registry.
9. Выберите срок регистрации.
10. Проверьте стоимость первого периода и обычного продления.
11. Уберите ненужные дополнительные услуги: hosting, website builder, платную почту и дополнительные сертификаты всегда можно подключить позже.
12. Оплатите регистрацию.
13. Дождитесь появления домена в панели управления.

После регистрации проверьте дату окончания домена и настройки Auto-Renew.

> [!TIP]
> Для инфраструктурного домена полезно сразу сохранить данные registrar, recovery email, срок продления и порядок восстановления доступа в безопасном месте.

## 6. Пример для России: `.ru` через Timeweb

Ниже приведён обезличенный пример регистрации домена вида:

```text
<имя>.ru
```

Названия разделов Timeweb со временем могут немного меняться, но логика процесса остаётся той же.

### Шаг 1. Создайте учётную запись

Зарегистрируйтесь в Timeweb и подтвердите контактные данные, если этого требует текущий onboarding.

Покупать hosting или VPS вместе с доменом не требуется.

### Шаг 2. Подготовьте администратора домена

Для `.ru`, `.рф` и `.su` откройте раздел управления администраторами доменов и пройдите требуемую идентификацию через ЕСИА.

В панели Timeweb:

**Домены и SSL → Администраторы**

Проверьте персональные данные. Они должны соответствовать подтверждённой учётной записи Госуслуг.

### Шаг 3. Найдите свободный домен

Откройте:

**Домены и SSL → Купить домен**

Введите желаемое имя:

```text
<имя>.ru
```

Если оно занято, выберите другое.

### Шаг 4. Проверьте заказ

Перед оплатой проверьте:

- точное доменное имя;
- выбранную доменную зону;
- администратора домена;
- срок регистрации;
- стоимость регистрации;
- стоимость последующего продления.

Дополнительный hosting для этой инструкции не требуется.

### Шаг 5. Оплатите регистрацию

Выберите доступный способ оплаты и завершите заказ.

После обработки платежа домен появится в разделе управления доменами. Регистрация и DNS-related changes могут отображаться не мгновенно.

### Шаг 6. Проверьте результат

Убедитесь, что:

- домен зарегистрирован на правильного администратора;
- дата окончания регистрации ожидаемая;
- доступ к панели registrar работает;
- настройки Auto-Renew соответствуют вашему плану.

> [!NOTE]
> На этом регистрация домена завершена. DNS можно оставить у Timeweb либо передать отдельному DNS-провайдеру.

## 7. DNS: что нужно понимать

Домен делегируется **authoritative DNS servers**. У регистратора эта делегация хранится в виде NS-серверов.

Пример:

```text
ns1.dns-provider.example
ns2.dns-provider.example
```

DNS может обслуживаться:

- самим регистратором;
- hosting provider;
- отдельным DNS-провайдером;
- Cloudflare;
- собственной DNS-инфраструктурой.

Регистратор и DNS-провайдер — разные роли. Домен можно оставить зарегистрированным у одной компании, а authoritative DNS разместить у другой.

### DNS остаётся у регистратора

Менять NS не требуется. Создавайте нужные DNS records в панели registrar.

```text
A       host.example.com       203.0.113.10
AAAA    host.example.com       2001:db8::10
CNAME   www.example.com        host.example.com
```

Диапазоны `203.0.113.0/24` и `2001:db8::/32` используются здесь только как документационные примеры.

### Используется отдельный DNS-провайдер

Сначала добавьте домен у выбранного DNS-провайдера. Он сообщит authoritative NS, которые нужно установить у регистратора.

Затем:

1. откройте управление доменом у registrar;
2. найдите настройки nameservers / NS;
3. замените текущий набор NS на выданный новым DNS-провайдером;
4. сохраните изменения;
5. дождитесь обновления делегирования.

> [!WARNING]
> Используйте только NS, выданные именно для вашего домена или аккаунта. Не копируйте nameservers из чужих инструкций или скриншотов.

## 8. Проверка DNS

Проверьте authoritative nameservers:

```sh
nslookup -type=NS example.com
```

Проверьте конкретный hostname:

```sh
nslookup host.example.com
```

Для IPv4/IPv6 можно дополнительно проверить записи:

```sh
nslookup -type=A host.example.com
nslookup -type=AAAA host.example.com
```

Смена NS и обновление DNS не всегда распространяются мгновенно. В зависимости от registrar, registry и DNS caches это может занять от нескольких минут до нескольких часов.

> [!NOTE]
> Если сразу после изменения видны старые NS, это ещё не означает ошибку. Сначала дождитесь распространения делегирования и проверьте результат повторно.

## 9. Dynamic DNS для меняющегося WAN IP

Если OpenWrt получает **публичный, но динамический** IP, direct MTProto/MTProxy удобнее привязать к hostname и обновлять его через DDNS.

Логика выглядит так:

```text
ISP changes WAN IP
       |
       v
DDNS client on OpenWrt
       |
       | DNS provider API
       v
A / AAAA record is updated
       |
       v
mt.example.com points to the current WAN IP
```

DNS-провайдер для такого сценария должен предоставлять API либо штатный механизм Dynamic DNS. Cloudflare — один из возможных вариантов, но не единственный.

> [!IMPORTANT]
> Для direct proxy запись должна вести на реальный маршрутизируемый WAN address. Если провайдер использует CGNAT, DDNS корректно обновит имя, но входящее соединение всё равно не станет доступным.

## 10. DNSSEC

DNSSEC добавляет криптографическую проверку DNS-ответов и помогает защититься от подмены DNS-данных.

Если DNSSEC ранее не использовался, безопаснее:

1. завершить настройку DNS-провайдера;
2. убедиться, что домен разрешается правильно;
3. только после этого включить DNSSEC.

Если DNSSEC уже активен и вы меняете DNS-провайдера, следуйте процедуре миграции обоих провайдеров. Старая DS-запись вместе с новыми NS может сделать домен недоступным для validating resolvers.

> [!WARNING]
> Не меняйте DNS-провайдера, оставляя активную старую DS-запись, если не понимаете точную процедуру DNSSEC migration.

## 11. Защита домена

Домен — часть инфраструктуры. Доступ к registrar нужно защищать так же серьёзно, как доступ к серверу или роутеру.

Рекомендуется:

- включить MFA/2FA;
- использовать уникальный пароль;
- включить Registrar Lock, если доступен;
- проверить recovery email и номер телефона;
- настроить Auto-Renew в соответствии со своей политикой;
- заранее убедиться, что способ оплаты останется рабочим к моменту продления;
- хранить MFA recovery codes в безопасном месте;
- включить DNSSEC после стабилизации DNS.

> [!CAUTION]
> Не публикуйте документы владельца, данные ЕСИА/Госуслуг, платёжные данные, recovery codes и session cookies панели registrar.

## 12. Минимальный пример: Cloudflare DNS

Cloudflare — один из возможных DNS-провайдеров. Его authoritative DNS доступен на Free plan, поэтому его удобно использовать как один из вариантов для этой схемы.

### Подключение домена

1. Зарегистрируйте домен у подходящего registrar.
2. Добавьте существующий домен в Cloudflare Dashboard.
3. Проверьте обнаруженные или импортированные DNS records.
4. Cloudflare покажет два authoritative nameservers для вашей зоны.
5. У registrar замените текущие NS на эту пару.
6. Дождитесь статуса зоны **Active**.
7. Проверьте делегирование:

```sh
nslookup -type=NS example.com
```

В ответе должны отображаться NS, назначенные Cloudflare именно вашему домену.

### Cloudflare как DDNS-провайдер

Для direct MTProto/MTProxy с динамическим публичным IP Cloudflare DNS можно использовать и как основу DDNS: клиент на OpenWrt или внешний скрипт определяет текущий WAN-адрес и через Cloudflare API обновляет `A` или `AAAA` запись выбранного hostname.

```text
OpenWrt WAN IP
      |
      v
DDNS client
      |
      | Cloudflare API
      v
mt.example.com -> current public IP
```

Конкретная настройка DDNS зависит от выбранного OpenWrt-пакета или скрипта и не относится к процессу регистрации домена.

> [!NOTE]
> Cloudflare здесь является **примером DNS/DDNS-провайдера**, а не обязательным компонентом регистрации домена.

Подробная настройка Cloudflare Tunnel, установка `cloudflared`, создание Published Application и подключение WEB Proxy описаны отдельно: **[Cloudflare Tunnel на OpenWrt](CLOUDFLARE.md)**.

## 13. Другие варианты DNS

Cloudflare использовать необязательно. DNS можно обслуживать у registrar или у любого другого провайдера, соответствующего вашим требованиям.

При выборе учитывайте:

| Критерий | Зачем он нужен |
|---|---|
| **Надёжность** | Домен должен стабильно разрешаться из Интернета |
| **DNSSEC** | Защита целостности DNS-ответов |
| **API** | Автоматизация и DDNS |
| **Dynamic DNS** | Автообновление `A` / `AAAA` при смене WAN IP |
| **Географическая доступность** | Сервис должен работать в вашей стране |
| **Ограничения аккаунта** | Важны доступность продуктов и способов оплаты |
| **Стоимость** | Особенно при долгосрочном использовании |

Для `telEgo-openwrt` важен не бренд DNS-провайдера, а корректно зарегистрированный домен и полный контроль над его DNS records.
