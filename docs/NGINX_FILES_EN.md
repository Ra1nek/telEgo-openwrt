# `nginx-telego` Nginx file ownership

[Русский](NGINX_FILES.md) · **English**

This document defines the **P6 — Managed Nginx File Ownership** contract. Its purpose is to state unambiguously which Nginx files belong to `nginx-telego`, which files are generated, and how manual filesystem drift is detected.

P6 intentionally **does not mutate** files. It only builds a reliable inventory and classifies drift. Repair, disable, restore, delete, and reconciliation belong to later stages and must share one transactional `nginx -t` / rollback path.

## Source of truth

User-facing ingress configuration lives in UCI:

```text
/etc/config/nginx_telego
```

The package-owned file set is declared by the versioned registry:

```text
/usr/share/nginx-telego/ownership.tsv
```

Canonical package copies of static Nginx files live outside the active include tree:

```text
/usr/share/nginx-telego/templates/
├── telego.conf
└── telego.locations
```

An active file never becomes the canonical source merely because it was edited by hand. For package-owned files, the canonical copy under `/usr/share/nginx-telego/templates/` remains authoritative.

## Registry v1

`ownership.tsv` has five TAB-separated fields:

```text
path    role    ownership    presence    source
```

The current registry declares:

| Path | Role | Ownership | Presence | Source |
|---|---|---|---|---|
| `/etc/nginx/conf.d/telego.conf` | `core` | `package` | `required` | `/usr/share/nginx-telego/templates/telego.conf` |
| `/etc/nginx/snippets/telego.locations` | `locations` | `package` | `required` | `/usr/share/nginx-telego/templates/telego.locations` |
| `/etc/nginx/conf.d/zz-telego-managed.conf` | `ingress` | `generated` | `conditional` | `renderer` |

Active generated-file names may still change before a stable release. The registry is the ownership contract; it is not a promise to keep the historical `zz-telego-managed.conf` name forever.

## Ownership types

### `package`

The active file has a canonical package copy and can be repaired from it in a future P7 stage.

Manual changes to the active file are drift. They are not adopted as new package configuration.

### `generated`

The file is rendered from UCI/runtime state. Generated ingress ownership is confirmed by the exact marker:

```text
# Generated by /usr/libexec/nginx-telego-render from /etc/config/nginx_telego.
```

A regular file occupying the reserved path without this marker is classified as `foreign`.

## Presence

`required` means the file is expected whenever `nginx-telego` is installed.

`conditional` means the file may be absent when the corresponding managed feature is disabled.

## Package-owned states

| State | Meaning |
|---|---|
| `ok` | active file matches the canonical package copy |
| `modified` | active file is regular but its contents differ |
| `missing` | active file is absent |
| `invalid-type` | active path exists but is not a supported regular file; every symlink, including a dangling symlink, is classified here |
| `source-missing` | canonical package copy is absent |
| `source-invalid-type` | canonical source exists with an unsafe type such as symlink or directory |

Canonical-source failures take precedence because future Repair must never restore from a damaged source.

## Generated ingress states

| State | Meaning |
|---|---|
| `absent` | generated path does not exist; valid when the managed profile is disabled |
| `managed` | regular file contains the exact renderer ownership marker |
| `foreign` | regular file occupies the managed path but is not owned by the renderer |
| `invalid-type` | path is a symlink, directory, FIFO, or another unsupported type |

`foreign` is intentionally different from `managed`: the package must not claim an administrator/application file merely because the filename collides.

## Registry security boundary

The registry is not an arbitrary root-filesystem manifest. The helper validates:

- absolute paths with no `..`, `.` or empty path segments;
- `core` and `ingress` only as direct children of `/etc/nginx/conf.d/*.conf`;
- `locations` only as a direct child of `/etc/nginx/snippets/`;
- package repair sources only as direct children of `/usr/share/nginx-telego/templates/`;
- valid `role / ownership / presence` combinations;
- no duplicate managed paths;
- a non-empty source for every entry.

This restriction is established before write operations exist so P7 inherits an already constrained ownership namespace.

## Read-only helper

P6 installs:

```text
/usr/libexec/nginx-telego-files
```

Supported commands are:

```text
nginx-telego-files validate
nginx-telego-files list
nginx-telego-files status
```

`validate` validates the ownership registry.

`list` prints the registry after validation.

`status` emits one TAB-separated line per managed path:

```text
path    role    ownership    presence    state    source
```

The helper does not run `rm`, `mv`, rewrite files, reload Nginx, or change UCI.

## Other `/etc/nginx/conf.d/*.conf` files

P6 **does not make the entire `/etc/nginx/conf.d/` directory telEgo-owned**. Files installed by other applications or created by an administrator remain outside the ownership registry.

A future LuCI Nginx Files inventory may expose those files as custom/foreign and offer separate safe operations, but package-owned repair must not silently modify them.

## CI verification

P6 is checked at three levels:

1. Unit/integration fixtures validate the registry, drift states, symlink/directory/FIFO cases, and path-boundary rules.
2. APK layout verification extracts the built `nginx-telego` APK and checks the registry/templates/helpers for presence, modes, and root ownership.
3. OpenWrt rootfs smoke installs the actual APK on supported OpenWrt 25.12.x releases and verifies the installed filesystem layout.

## P6 / P7 boundary

P6 answers:

> Which Nginx files belong to `nginx-telego`, and what state are they in?

P7 will answer:

> How can the real filesystem be reconciled safely to the UCI desired state?

Until P7, `modified`, `missing`, `foreign`, and `invalid-type` are diagnostics only; they are not automatic requests to change the filesystem.
